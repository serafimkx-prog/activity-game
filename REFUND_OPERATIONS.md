# Возвраты Self.PayAnyWay: внутренний runbook

Этот процесс нужен только для ручной сверки доступа после того, как продавец уже подтвердил возврат в Self.PayAnyWay. Он не инициирует денежный возврат, не отменяет чек и не является публичным self-service.

## До запуска

1. Сопоставить обращение с одной конкретной операцией провайдера и одним конкретным `purchase_orders.id`. Не выбирать заказ по email, имени пользователя, словарю или правилу «последний заказ».
2. В кабинете Self.PayAnyWay подтвердить, что денежный возврат завершён.
3. Подтвердить аннулирование НПД-чека или отдельное подтверждение провайдера, что возвратный чек создан автоматически.
4. Не переносить в команду provider operation ID, Telegram ID, реквизиты платежа или другие персональные данные. В инструмент передаётся только внутренний числовой ID заказа.

Если хотя бы один пункт не подтверждён, остановиться. Инструмент не должен опережать возврат денег.

## Dry-run

Положить только внутренний ID заказа в временный локальный файл с ограниченным доступом и выполнить из корня репозитория:

```bash
npx -y -p node@22 -p wrangler@4.149.0 node tools/refund_order.mjs \
  --remote --order-id-file <secure-temporary-file>
```

Dry-run включён по умолчанию. Ожидаемое состояние перед первой сверкой — `ready`. `already_reconciled` означает, что заказ уже закрыт и активных прав от него нет. `repair_revocation` — fail-safe состояние после прерывания: заказ уже закрыт для доступа, но техническую отметку права нужно довести повторным apply.

Любое несовпадение провайдера, продукта, суммы, валюты, факта оплаты, состава заказа или entitlement-строк завершает команду без изменений.

## Apply

Только после успешного dry-run и подтверждения продавца:

```bash
npx -y -p node@22 -p wrangler@4.149.0 node tools/refund_order.mjs \
  --remote --order-id-file <secure-temporary-file> \
  --apply --refund-confirmed
```

Оба флага обязательны. Результат не печатает ID заказа, пользователя, операции провайдера, платёжные реквизиты или raw payload.

После команды удалить временный файл и повторить ту же apply-команду. Повтор должен вернуть `already_reconciled` и `activeEntitlementCount: 0` без новых изменений.

## Почему прерывание безопасно

Инструмент сначала условно меняет только выбранный заказ с `succeeded` на `refunded`. Текущий запрос доступа учитывает только заказы со статусом `succeeded`, поэтому доступ закрывается сразу. Затем инструмент отзывает только entitlement-строки этого заказа.

Если процесс прервётся между шагами, доступ уже закрыт; повторный запуск распознает `refunded` с ещё активной строкой как `repair_revocation` и завершит отзыв. Callback replay не возвращает права закрытому заказу. Соседние заказы и `user_dictionary_access` не изменяются.

## Проверка после apply

- выбранный заказ: `refunded`;
- его активные `purchase_order_entitlements`: `0`;
- другие заказы и ручные права не изменились;
- `https://activity-game.ru/api/config` по-прежнему возвращает `paymentCheckoutReady: true`;
- неавторизованный запрос premium JSON по-прежнему получает `401`.

Инструмент не публикуется в assets (`tools/` исключён через `.assetsignore`), не добавляет Worker endpoint, форму или кнопку возврата. Нового deploy и миграции схемы для него не требуется.
